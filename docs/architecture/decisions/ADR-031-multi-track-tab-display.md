# ADR-031 Simultaneous multi-track TAB display (Phase 6b-2)

Status: Accepted (2026-11-06). The acceptance criteria were fixed before any code. The user accepted all four choices of section 5 as proposed on 2026-11-06. 6b-2 is done when it meets section 4.
Date: 2026-11-06

## Context

The MVP shows one active TAB track at a time (Q-17); simultaneous multi-track display was deferred to Phase 6b. The roadmap groups it with track mixer basics (6b-3) and MusicXML export (6b-4).

Findings from the code (not assumptions):

- `mc_notation::layout_tab(score, track, metrics)` lays out **one track**. Bar widths come from that track's content only (one column per distinct onset, logarithmic duration spacing), so two tracks laid out separately do not line up.
- A `SystemLayout` holds one stave. Hit regions are `[bar, string, voice, slot]` with no track. Dart caches one layout per `(revision, activeTrack, width, zoom)` and paints one `SystemPainter` per system.
- The playback cursor maps a tick to x through the system's bar x-positions only (track independent).
- There is no per-track "visible" state anywhere. Mute is session state in `TransportState` (ADR-028, Q6), not document content.
- Cost today: a whole track is laid out on every revision. 1.3 to 1.6 ms for a typical track, 5.8 to 8.6 ms for a large one (phase-3 exit report, O-7). The fixtures are TYPICAL (4 tracks x 150 bars) and LARGE (20 tracks x 300 bars x 16 beats x 3 notes). Laying out all 20 large tracks the same way would cost on the order of 100 ms or more, far over budget.

## Decision

### 1. Layout in Rust, one system holds one stave per visible track

`mc-notation` gains `layout_score(score, tracks: &[TrackId], metrics) -> ScoreLayout`.

- A system holds one **stave** per requested track, in score track order, stacked vertically.
- **Bar lines line up** across staves: every stave of a system has the same bar x-positions and widths.
- Line breaking and justification are computed once for the whole system, from the combined bar plans.
- Each stave carries its own lines, glyphs and hit regions in **stave-local coordinates**, plus its vertical offset in the system. Dart can therefore reuse `SystemPainter`, hit testing, the cursor and the selection painter per stave unchanged.
- `layout_tab` stays and keeps its output exactly. With one track, `layout_score` produces the same stave as `layout_tab`. The existing goldens are not changed.
- Diagnostics (D-01) are per stave: a bar is tinted only on the track that is underfull or overfull.

### 2. Visibility is UI state

- The set of shown tracks lives in the Dart editor state (`EditorState`), like `activeTrack`. It is not stored in the document and not part of undo.
- There is no format change, and the core has no notion of "visible". Dart passes the list of tracks to the layout call, as it passes metrics today. Musical layout stays in Rust (ADR-018, GR-05).
- Ids of deleted tracks are pruned, as `activeTrack` already is.
- The track list gets a show/hide control per track.

### 3. Editing stays on the active track

- The cursor, selection, inspector and keyboard keep acting on `activeTrack`. They are drawn only on its stave.
- A click on another stave makes that track active and places the cursor there, in one click.
- No editing command changes because of multi-track display.

### 4. FFI

- `DocumentHandle::score_layout(tracks: Vec<i64>, metrics) -> ScoreLayoutDto`, `#[frb(sync)]` like `tab_layout`.
- A system is `{ index, y, height, bars, staves: [{ track, strings, top, system: SystemDto }] }`. The per-stave payload is today's `SystemDto` in stave-local coordinates.
- Bindings are regenerated by codegen only (FF-12). Public API snapshots change by additions only (FF-22).

## 4. Acceptance criteria (fixed before implementation)

Measured on the reference machine (single machine, ADR-025). Thresholds are not lowered to match a result. If a performance criterion fails, the fallbacks of section 6 are applied in order and measured again. If they still fail, the scope is reduced with the user (section 6). The threshold is not changed.

| Id | Criterion | How it is checked |
|---|---|---|
| M1 | With one track, `layout_score` yields exactly the stave of `layout_tab` (same bars, lines, glyphs and hits) on every fixture; existing goldens unchanged | Equivalence test over SMALL, TYPICAL, feature-rich and reference fixtures |
| M2 | In every system, all staves have identical bar indices, x and widths | Property test over random multi-track scores |

## 5. User decisions (2026-11-06: all four as proposed)

Decided: (1) align by onset across staves; (2) all tracks shown by default; (3) the active track cannot be hidden; (4) visibility is not remembered in 6b-2. The options considered are kept below.

1. **Column alignment.**
   - Proposed: **align by onset across staves**. Columns are the union of onsets of all shown tracks in the bar, so notes played together sit in one vertical line, as in common multi-track TAB editors. Each column is as wide as the widest note in it, across tracks.
   - Alternative: only bar lines line up, and each stave spaces its own beats. This is simpler, but simultaneous notes drift apart.
2. **Default visibility.**
   - Proposed: **all tracks shown** when a document opens.
   - Alternative: only the active track shown, like today, with the user adding others.
   - The answer matters for P3 if the large score is the default case.
3. **Hiding the active track.**
   - Proposed: **not allowed**. The hide control is disabled for the active track, so the cursor always has a stave.
   - Alternative: hiding it makes the next shown track active.
4. **Remembering visibility.**
   - Proposed: **not remembered** in 6b-2. It resets when a document opens, as mute does (session state).
   - Alternative: remember it per document in workspace preferences (not in `.giproj`).

## 6. Performance fallbacks, in order (only if P1 to P4 fail)

1. **Bar-plan cache keyed by content identity.**
   - Bar contents are `Arc`s with structural sharing (ADR-016), so an unchanged bar keeps its pointer across revisions.
   - Cache each track's bar plan by `(track, bar, Arc pointer, master bar, metrics)`. Only edited bars are re-planned.
2. **Emit only the systems in view.**
   - Line breaking still covers the whole score, so system boundaries stay stable, but lines, glyphs and hits are emitted only for systems in a requested range.
   - Dart already virtualizes systems.
3. **Scope reduction, decided with the user.** For example, a cap on how many tracks are shown by default on large scores. This is a scope change, not a threshold change.

## Alternatives

- **Lay out each track separately in Rust, and line up bars in Dart.** Rejected: bar widths and column spacing are layout decisions (ADR-018). Dart would have to move glyphs it did not lay out.
- **Store visibility in the document.** Rejected for now: it has no musical meaning, would need a format bump (GR-08), and mute (the nearest precedent) is session state.
- **A new crate for score layout.** Rejected: it is the same bounded context as `layout_tab` (no empty or duplicate crates).

## Trade-offs

- Onset alignment makes a bar as wide as the busiest track needs. A sparse track next to a dense one gets wide gaps, which is the expected look of aligned multi-track TAB.
- Showing many tracks makes each system tall, so fewer bars fit on screen vertically. The show/hide control is the user's tool for this.

## Consequences

- `mc-notation`: a new entry point and types; `layout_tab` is unchanged.
- `mc-app`: a new query.
- `mc-ffi`: a new DTO and call.
- `core_bridge`: the method on both the real and the fake service, plus the shared contract.
- `editor_feature`: `visibleTracks` state, a multi-stave `TabView` and the track list control.
- The app bench gains multi-track cases.
- Known-limitations loses the one-active-track item and gains whatever choice 5.4 leaves open.

## Related fitness functions

FF-03 and FF-04 (`mc-notation` purity and wasm), FF-12, FF-21 (benchmark regression), FF-22, FF-34.

## Reconsideration conditions

- Standard notation (6c) adds staves of a different kind and density, which would revisit the stave model.
- A second platform with small screens (Phase 7) may need a different default visibility.

## Fallback 2: emit only the systems in view (6b-2b, user decision 2026-11-06)

The user chose to apply fallback 2 before fallback 1, because the measured breakdown shows fallback 1 alone cannot pass.

**API.**
- `outline_score` does the line breaking for the whole score: system positions, heights, bar ranges and justification.
- `layout_score_systems(outline, range)` measures and emits only the requested systems.
- `layout_score` is these two composed, and its output is unchanged.
- `mc-app` keeps the outline per (revision, tracks, metrics), so the outline and the systems fetched for the view come from one state.
- FFI: `score_outline` and `score_systems(first, count)`, both sync. The outline DTO carries no track list, because a returned `Vec<i64>` becomes `BigInt`s in Dart. Each stave carries its track id instead.
- Dart sizes the virtualized list from the outline and fetches systems in batches of 4 when items are built.

**Equivalence.**
- `layout_tab` and `layout_score` fingerprints before and after the split: 20 of 20 identical on the fixtures.
- Windowed layout equals the full layout on more than 900 random ranges over 300 seeded scores.
- A stale outline (bars or tracks changed) is an error, not a panic.

**Measured, reference machine (ADR-025).**

| Id | Rust bench (edit plus outline plus 3 systems) | In the app, profile build, every track shown (`app/tool/edit_latency.dart`) | Budget | Result |
|---|---|---|---|---|
| P1 TYPICAL, 4 tracks | p99 1.2 ms | Compute bound (command plus frame build plus raster, p99 summed) 13.4 ms; 0 edits missed the next frame | 16 ms | Pass |
| P2 LARGE, 4 tracks | p99 4.3 ms | not measured yet (the tool shows every track) | 33 ms | Pass (Rust only) |
| P3 LARGE, 20 tracks | p99 14.1 ms | Edit to frame p50 40.9 ms, **p99 63.3 ms**. Frame build p99 50.9 ms, raster p99 21.7 ms. Layout query in view (FFI included) p50 19.7 ms, p99 36.2 ms | 33 ms | **Fail end to end** |
| P4 TYPICAL scroll | — | Build plus raster per frame p99 5.4 ms, 0 frames over 33 ms (300 frames) | 16 ms; none over 33 ms | Pass |

The Rust-only bench number for P3 is within budget, but the budget in performance-requirements is for the whole path, so P3 is recorded as **failing**. It is not passed on the bench number.

In the app, most of the frame build is the synchronous layout query made during build. Each revision recomputes the outline, which measures every bar of all 20 tracks (13 to 20 ms). This is what fallback 1 (the bar-plan cache) removes, so it is applied next. For reference, LARGE scroll with 20 tracks gave p99 24.0 ms and 1 frame over 33 ms. P4 sets a budget for TYPICAL only.

## Fallback 1: bar-width cache (6b-2c, 2026-11-06)

`LayoutCache` and `outline_score_cached` keep each bar's natural widths across revisions. The key for a bar is:
- the `Arc` of its content in every shown track, compared with `Arc::ptr_eq` (edits copy only what they change, ADR-016);
- its master bar;
- the previous bar's time signature;
- the shown tracks and the metrics.

The cache holds the `Arc`s it keys on, so an address cannot be freed and reused by other content. The `mc-app` session keeps one cache.

Tests:
- The cached outline equals a fresh outline after every kind of change: note edits, inserted bars, time-signature changes, added and removed tracks, other shown tracks and other metrics. This was checked over 60 seeded scores × 25 steps.
- A note edit re-measures exactly one bar, and a repeated request measures none.
- Two deliberate mutations of the key are caught: one drops the previous-time-signature check, the other drops the `Arc` comparison.

**Measurement note.** The first two end-to-end TYPICAL runs after this change looked worse than before. An A/B run was then started, but it overlapped with an interrupted command that kept running in the background, so two instances of the tool ran at once and wrote the same files. Those numbers were **discarded**.

The protocol was then made strict:
- one tool instance at a time, refusing to start while another runs;
- a distinct output file per run;
- several runs per case, reported as median and range.

Clean results, reference machine (ADR-025), profile build, `app/tool/edit_latency.dart`:

| Id | Runs | Edit to frame p99 | Compute bound (p99 summed) | Edits missing the next frame | Layout query in view (FFI incl.) p99 | Budget | Result |
|---|---|---|---|---|---|---|---|
| P1 TYPICAL, 4 tracks | 5 | median 16.1 ms (15.3 to 32.8) | median 11.2 ms (10.7 to 16.8) | 0/200 in 4 runs, 20/200 in 1 | 0.6 to 0.9 ms | 16 ms | **Pass** (compute 11.2 ms; the outlier run had build and raster both up together, machine noise) |

In the Rust bench, an edit plus outline plus 3 systems on LARGE with 20 tracks is now p99 1.8 ms (it was 14.1 ms).

- frame build p99 23 to 28 ms, which includes the synchronous layout query of about 7 ms;
- raster p99 16 to 22 ms;

Both fallbacks of section 6 are now applied, so step 3 (scope reduction, decided with the user) is next. The threshold is not changed.

- a 16-stave system is about 1984 px;
- every stave of a system item is built and painted even when only a few are on screen.

## Step A: build only the staves in view (6b-2d, user decision 2026-11-07)

The user chose a timeboxed attempt (A) before the scope reduction (B).

**Change.** The TAB list now has one item per stave instead of one per system, so the virtualized list builds and paints only the staves in view. A 20-stave system is about 2480 px tall, taller than the window.
- The playback cursor is drawn on every stave at the same x, so together the segments span the system without gaps. M5 is now tested that way.
- No API, Rust or threshold change.

**Result: A alone does not pass P3.** 2026-11-07, protocol of the previous section. Runs where the window was minimized are marked TAINTED and discarded; there were 2 such runs.
- LARGE with 20 tracks: 18.6, 47.9, 38.0, 38.1, 55.7 ms edit-to-frame p99. Median 38.1 ms, 1 of 5 within 33 ms.
- TYPICAL: 15.1, 16.0, 17.0 ms; compute 10.4 to 12.6 ms. Still passes.

**Step B applied (scope reduction).**
- A document opens with at most `maxShownTracksOnOpen` = 16 tracks shown. The rest start hidden and can be shown with the eye button. Tracks added later are shown.
- The track list says how many tracks are hidden.
- 16 was taken from the 2026-11-06 sweep, where it was the largest count within budget.
- Tests check the cap on open, and that adding tracks does not hide them.

**Measurement drift, not resolved.** Later on 2026-11-07, the same machine measured much slower for the same code:

| Build | LARGE shown | Edit to frame p99 | p50 | Raster p99 |
|---|---|---|---|---|
| A (per-stave items) | 16 | 42.0, 44.5, 45.3, 47.3 ms | 23 to 27 ms | 24 to 30 ms |
| A | 20 | 38.5, 48.9 ms | 18 to 26 ms | 14 to 33 ms |
| Unchanged code of `a1a59ef` (per-system items) | 16 | 45.8, 46.1, 50.4 ms | 28 to 29 ms | 23 to 31 ms |
| Same code, 2026-11-06 | 16 | 17.0, 25.9 ms | 13.4 ms | 9 to 12 ms |

The unchanged code moved from 17 to 26 ms to 46 to 50 ms, so the difference is the machine state, not the code.

Not the cause, as checked:
- CPU: no throttling ("% Processor Performance" 111 to 120%).
- GPU: idle between runs.
- Display: one 1920x1080 display at 74 Hz; at 74 Hz the 13.3 ms p50 is exactly one frame.
- Power: desktop on the Balanced plan, no battery.

The IDE and its Dart analysis server used 2 to 3 cores during some runs. The cause is **not found**.

**Status of the performance criteria.**
- **P1 and P4 (TYPICAL) pass on both days.**
- **P2 and P3 are not established.** P2 passed on 2026-11-06 and did not on 2026-11-07 under the same code, and P3 did not pass on either day.
- The 16-track cap is kept as the scope reduction the user approved. It is not claimed to meet the budget until P2 is re-measured under controlled conditions.
- Thresholds are unchanged.
